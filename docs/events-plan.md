# Events — implementation plan

Working plan. Delete after the change ships.

> **Scope note:** Email subscribers + campaign sends are **deferred to a
> future phase** — see [Deferred: subscribers & campaigns](#deferred-subscribers--campaigns)
> at the bottom. This phase is events + paid registration + the admin
> surface. No public subscribe form, no batch email campaigns.

## What we're adding

A first-class **Events** feature: a public listing + detail page, paid
registration via Razorpay, and an admin surface to manage signups,
refunds, expenses, discount codes, and **carpool/transport planning**.
Transport is **two-sided** (an evolution of the admin-only legacy
`/eat/:slug` planner): attendees self-report their travel — start point,
pickup point, whether they're driving — via a per-event form that
remembers their usual setup; admins consume that to group the carpool.
(Transactional post-payment email only — subscriber campaigns come later.)

Legacy lived across two repos (`blrhikes/` Astro + `blrhikes-webhook-listeners/`
Hono Worker, both on Supabase). We're collapsing it into the v2 monorepo:
PayloadCMS (D1) for data + admin, React Router web for the public surface,
and a small webhook handler — almost certainly inside the CMS Next worker —
for Razorpay events.

## What we're explicitly *not* repeating from the legacy app

The legacy events system grew organically; the rebuild deliberately avoids
these:

1. **GitHub issues as the master event record.** Legacy synced GitHub
   issues → `events` table via webhook, then admin views read from both
   sources (with sync windows, drift). New: events are Payload docs.
   Period.
2. **Weak FK from `payments.reason` → `events.text_id` (string match).**
   Legacy had no enforced relation; orphaned rows when slugs changed. New:
   `Registrations.event` is a real Payload relationship.
3. **Conflating registration with payment.** Legacy had an `event_attendees`
   table that was effectively unused — signups were inferred from
   `payments`. New: one `Registrations` collection holds intent + payment +
   status, with explicit transitions. [SM: Tell me more about how we will do this? inferring signups from payments is fine, no?]
4. **A 1,300-line `/eaa/[slug].astro` admin dashboard** that crashes if any
   one query fails. New: lean on Payload's built-in list/detail views with
   filters; only one custom view (per-event dashboard) and it stays small.
5. **Race-prone reserved-spot math** computed on page render with no
   transaction wrapping payment + spot allocation. New: spot allocation is
   atomic with payment confirmation; reserved-spot math is derived from
   stored counters, not recomputed via joins on every page load.
6. **Email body = first GitHub issue comment with a frontmatter flag.**
   New: post-payment email is a Lexical-rendered field on the event itself
   (or a small Templates collection if we end up reusing copy).

### `Registrations` collection

The single source of truth for "who is coming / who paid". Replaces legacy
`event_attendees` + the event-relevant subset of `payments`.

| field | type | notes |
|---|---|---|
| `event` | relationship → events, required | hard FK |
| `user` | relationship → users | optional; many registrants are not site users |
| `email` | email, required | always captured |
| `name` | text, optional | |
| `phone` | text | |
| `source` | select | `self` (paid via web) / `admin` (manually added) / `crew` (added from the crew roster) — how the row was created |
| `crew` | relationship → crew | set when `source === crew`; links back to the roster person |
| `countsTowardCapacity` | boolean, default true | admin can exclude comps/crew from the `maxAttendees` headcount |
| `status` | select | **payment lifecycle only** → `pending_payment` / `confirmed` / `cancelled` (see note below) |
| `attendance` | select | `unset` (default) / `attended` / `no_show` — admin-set *after* the event; orthogonal to payment |
| `listPriceRupees` | number, required | snapshot at time of registration |
| `discountCode` | relationship → discount-codes | nullable |
| `discountAppliedRupees` | number, default 0 | |
| `paidRupees` | number, default 0 | net of refunds = `paidRupees - refundedRupees` |
| `refundedRupees` | number, default 0 | running total |
| `paymentProvider` | select | `razorpay` / future providers |
| `providerOrderId` | text, indexed | provider-agnostic order id |
| `providerPaymentId` | text, indexed | populated on webhook |
| `transportToken` | text, indexed | generated on confirm; deep-links the attendee travel form without login |
| `notes` | textarea | admin scratch |
| `socials` | json | optional handles |

Payment ids are kept provider-agnostic (`paymentProvider` + `providerOrderId` +
`providerPaymentId`) so we can add or swap providers later without a schema churn.

**On `status` and `pending_payment`** — `status` tracks *only* the payment
lifecycle, not attendance (which is its own field above) and not reserved spots
(those are `Events.reservedHeldCount`, held by discount codes — a different
mechanism entirely). `pending_payment` is the **in-flight checkout window**: the
row + its spot-hold are created when we open the Razorpay order, and the webhook
flips it to `confirmed` on payment. We hold the spot during checkout (chosen over
"create the row only on payment") so a fast-selling hike can't sell the last seat
to three people racing through Razorpay at once. Abandoned checkouts sit
`pending_payment` and get swept (see Q2 — sweep-on-register). Transitions:

```
pending_payment ──(webhook: order.paid)──▶ confirmed
       │                                       │
       └──(swept after 30 min / user cancels)──┴──(refund/cancel)──▶ cancelled
```

Audit: Payload's built-in versioning (drafts off, but `versions: true`)
gives us per-change history for free — use it instead of writing a
custom audit table.

#### Adding attendees manually (admin)

Not everyone comes through the paid web flow — crew run the hike, some folks pay
offline, some are comps. The admin can **add an attendee directly** from the
per-event view (see [Admin surface](#admin-surface-cms-admin)). It creates a
`confirmed` Registration with `source: admin` (or `crew`), no Razorpay order,
`paidRupees` defaulting to 0 (editable). The "add" UI is a single search box over
**multiple people sources**, so the admin rarely retypes anyone:

1. **Crew** (pinned at top — volunteers & guides; they're on nearly every hike).
2. **Members** (`Users`).
3. **Past participants** (distinct emails from prior `Registrations`).
4. **+ New person** (free entry: name, email, phone) when nobody matches.

Picking a crew member sets `source: crew`, links `crew`, and defaults
`countsTowardCapacity: false` (staff usually shouldn't eat a paying spot — admin
can flip it).

### `SavedLocations` collection

A person's **one library of saved places** (generalizes the legacy
`start_locations` table). A saved place is role-agnostic — the *same* place can
be someone's start point for one event and their pickup point for another; the
role is assigned per-event in `EventTransportPrefs`, not baked into the record.
This is the "easy to manage" call: one list, no duplicate "start" vs "pickup"
entries. **Keyed by email, not user** — most registrants aren't members (legacy
got this right), with an optional `user` link for members.

| field | type | notes |
|---|---|---|
| `email` | email, required, indexed | the key; lookups are case-insensitive |
| `user` | relationship → users | optional; convenience link for members |
| `label` | text, required | e.g. "Koramangala 5th Block", "Silk Board flyover" |
| `mapsUrl` | text | Google Maps link |
| `isDefault` | boolean, default false | their *usual start* — cold-start prefill only (see prefill strategy below) |

Unique on `(lower(email), label)`; one default per email. Legacy enforced both
with partial unique indexes — Payload can't express those directly, so a
`beforeChange` hook clears other defaults for the email and a `beforeValidate`
guards the dup-label case (return the existing row, as legacy's add endpoint did).

### `EventTransportPrefs` collection (NEW — the attendee's self-reported travel)

One row per (attendee, event): what *they* told us about getting to this
specific event. This is the storage that makes transport **two-sided** without a
write race — each attendee owns their own row; the admin's `transportPlan` blob
stays admin-only. The admin planner reads these as its raw inputs.

| field | type | notes |
|---|---|---|
| `event` | relationship → events, required, indexed | denormalized for the planner's "all prefs for this event" query |
| `registration` | relationship → registrations, required | ownership; one pref per registration |
| `email` | email, required, indexed | snapshot; the cross-event prefill key |
| `travelMode` | select | `own_vehicle` / `needs_pickup` / `self_arranged` |
| `startLocation` | relationship → saved-locations | where they're coming from |
| `pickupSameAsStart` | boolean, default true | the easy-manage toggle; when true, pickup = start |
| `pickupLocation` | relationship → saved-locations | used only when `pickupSameAsStart` is false |
| `vehicle` | relationship → vehicles | when `travelMode === own_vehicle` |
| `seatsOffered` | number, default 0 | spare seats they'll give others this trip (≤ capacity − 1; a motorbike rider going solo sets 0 even though the bike seats 2) |
| `notes` | textarea | "can leave by 4am", "have space for 1 bag", etc. |

Roles, finally concrete: **start** = where you begin; **pickup** = where a
vehicle collects you. They collapse to one in the common case (`pickupSameAsStart`),
and *especially* when `travelMode === own_vehicle` (you're driving — pickup is
moot, toggle is forced true). Different only when you want to be met elsewhere
(e.g. start from home, but easiest to grab you at the highway toll).

**Prefill strategy** (answers "default to their typical start location"): when an
attendee opens the form, prefill the whole thing from their **most recent**
`EventTransportPrefs` (start, pickup, same-as-start, mode, vehicle) — that's
"their typical setup" for free, for *both* locations and their vehicle, not just
start. Cold start (first-ever event): start = their `isDefault` SavedLocation,
`pickupSameAsStart = true`, mode unset.

### `Vehicles` collection (NEW — the thing legacy never persisted)

Legacy re-typed each driver's seat count into *every* plan. This makes "who has
a vehicle and how many seats" durable, queryable, and reusable across events —
exactly your ask. Same email-keyed pattern as `SavedLocations`. Attendees pick
or create their vehicle in the self-report form (`travelMode === own_vehicle`).

| field | type | notes |
|---|---|---|
| `email` | email, required, indexed | owner; the key |
| `user` | relationship → users | optional; link for members |
| `type` | select | `car` / `suv` / `van` / `motorbike` / `other` — drives the icon (🚗/🏍️) + capacity sanity |
| `label` | text | e.g. "Swift", "Thar", "white Innova", "Classic 350" |
| `capacity` | number, required | total seats incl. rider/driver (car: 4–7; motorbike: **1 solo or 2 with pillion**) |
| `isDefault` | boolean, default false | one default per email; pre-fills type/capacity when picked as driver |
| `notes` | textarea | "AC iffy", "no boot space", "only short pillion rides", etc. |

**Multiple vehicles per person, different capacities** — Ravi can save a Swift
(5) *and* a Royal Enfield (2); `isDefault` marks the usual one, and the
self-report form lets him pick which he's bringing to *this* event. Capacity is a
property of the *vehicle*, so the planner always knows the right seat count.

**Motorbikes + the optional pillion**: a bike's `capacity` is its physical max
(2 incl. rider), but whether the rider actually takes a pillion is a *per-event*
choice — that's `EventTransportPrefs.seatsOffered` (0 = riding solo, 1 = happy to
carry one). So "I have a bike but I'm not taking anyone today" is `capacity: 2,
seatsOffered: 0`. The model already separates "what the vehicle can hold" from
"what I'm offering this trip," which is exactly the refuse-a-pillion case.

The per-event plan still **snapshots** capacity inline (admin can override for a
specific trip without mutating the saved vehicle — same freeze-on-use behavior
as start locations). Picking a driver pre-fills capacity/label from their
default `Vehicle`; editing the plan doesn't write back.

**One person can have several vehicles** (Swift + the family Innova); `isDefault`
marks the usual one. A `Vehicle` is associated to a person by `email` (always)
and to a `users` row when they're a member (`user`) — so vehicle ownership is
discoverable from both directions.

### "Who has a vehicle?" — vehicle discoverability (NEW — your invite-the-drivers ask)

Because `Vehicles` is a real collection (not buried in a plan blob), "who can
drive" is a query, not a memory. Two surfaces:

- **Member list**: a `hasVehicle` / seat-count column + filter on the Users admin
  list, derived from related `Vehicles`. Filter to "members with a vehicle" (and
  by `type` — e.g. cars+SUVs only when you need real passenger capacity) → bulk
  context for an invite.
- **Drivers directory** (custom admin view, or a filtered `Vehicles` list):
  *everyone* with a saved vehicle — **members and past non-member participants
  alike** (the email key means a one-off attendee who once drove still shows up).
  Columns: name, vehicle (type icon + capacity), phone/email, last event
  attended, member?. This is the "pull up the list of vehicle-owners and invite
  them" view.

Surfacing this needs nothing new in the data model — just `Vehicles` joined to
`Users` (members) and to past `Registrations` (non-members, by email). The
"invite" action itself is out of scope for v1 (copy emails / open WhatsApp); a
real invite-send rides the deferred subscriber/campaign phase.

## Public web surface (apps/web)

New routes:

```
/events                  → routes/events.tsx          (listing — upcoming + past)
/events/:slug            → routes/event-detail.tsx    (detail + register CTA)
/events/:slug/register   → routes/event-register.tsx  (form → Razorpay order)
/events/payment-success  → routes/event-payment-success.tsx
/events/:slug/travel     → routes/event-travel.tsx    (attendee self-report transport form)
```

Listing reads from CMS REST: `GET /api/events?where[status][equals]=live`.
Detail page renders `description` Lexical. Register page POSTs to
`/api/events/register` (CMS endpoint — see below) which returns a Razorpay
order; client opens Razorpay checkout; on success redirects to
`/events/payment-success`.

### Attendee transport form (`/events/:slug/travel`)

The self-report side of transport. Filled **after paying** (a separate, optional
step — confirmation email links straight to it; not in the checkout flow).

**Access** (most registrants aren't members — legacy keyed off email):
- **Tokenized link** in the post-payment email: `?t=<registration-token>` opens
  *their* row, no login. Same token pattern we'd use for unsubscribe.
- **Logged-in members** also reach it from the event page; we match their
  registration by email.
- The token resolves a single `Registration` → its `EventTransportPrefs` row
  (created on first save). Never trust an email in the query string alone.

The form: start location (prefilled to their usual — see prefill strategy),
a **"pickup same as my start" toggle** (on by default), pickup location when
it's off, and "I'm driving" → pick/add a `Vehicle` + seats offered. All
locations and vehicles draw from / write to their cross-event `SavedLocations`
+ `Vehicles` libraries, so next event is one-tap. Progressive-enhancement
Tailwind form; posts to a CMS endpoint (below) that owns the token check.

## CMS endpoints (custom routes inside the Next/Payload worker)

Payload has built-in REST/GraphQL for CRUD; we only need custom endpoints
where there's logic Payload won't do for us:

| method | path | purpose |
|---|---|---|
| `POST` | `/api/events/register` | Enforce the registration window (incl. **driver-only gate** — see [Driver-priority registration](#driver-priority-registration)), validate event + maxAttendees + spot, allocate atomically, create `pending_payment` Registration (+ seed `Vehicle`/`EventTransportPrefs` for drivers), create Razorpay order, return order id |
| `POST` | `/api/webhooks/razorpay` | Verify signature; on `order.paid` mark Registration `confirmed`, increment `Events.paidCount`, queue post-payment email |
| `POST` | `/api/events/:id/add-attendee` | Admin-only: cross-source people search (crew/members/past/new) → create a `confirmed`, payment-exempt Registration |
| `GET`  | `/api/transport-prefs` | Resolve `?t=<token>` (or logged-in member) → their `EventTransportPrefs` + saved-location/vehicle libraries + last-event prefs for prefill |
| `POST` | `/api/transport-prefs` | Token/member-gated upsert of the attendee's prefs; may also create a `SavedLocation`/`Vehicle` inline. The *only* custom transport endpoint — the rest is Payload REST |

`Registration` gains a `transportToken` (text, indexed, generated on confirm)
so the post-payment email can deep-link the form without auth. Member access
falls back to matching `Registration.email`.

Why inside the CMS worker rather than a separate Worker (the legacy
`blrhikes-webhook-listeners` shape):
- The CMS worker already has D1 + Payload local API + Resend. Splitting
  duplicates env wiring and adds an HTTP hop that has to authenticate
  back into Payload anyway.
- Razorpay webhooks need DB writes; they are the obvious case for "do
  it where the data lives".

Custom routes go in `apps/cms/src/app/(payload)/api/.../route.ts` (already
how Payload mounts; the `my-route` directory is the existing example).

## Admin surface (CMS admin)

Default Payload list/detail views handle 80% of this for free:

- Events list: filter by status, sort by startAt
- Registrations list: filter by event, status, paid/unpaid
- Refunds list: filter by event (via registration)
- DiscountCodes list: filter by event
- Expenses list: filter by event
- **Drivers directory**: `Vehicles` list (everyone with a vehicle — members +

The one custom view: **per-event dashboard** at
`/admin/collections/events/:id/dashboard` — pulls counters, the
registrations table for that event, refunds, and expenses. Built as a
Payload custom view (small React component), not 1,300 lines of inline JSX.
(The "send campaign" button on this dashboard arrives with the subscriber
phase.)

**Add attendee** lives on this dashboard (and/or as a Registrations list action):
a search box over crew → members → past participants → new person (see
[Adding attendees manually](#adding-attendees-manually-admin)). Backed by a small
custom endpoint (`POST /api/events/:id/add-attendee`) that creates the
`confirmed`, payment-exempt Registration — the cross-source people search is the
one bit Payload's stock relationship field can't do.

Discount-code generation can live inline on the event detail (custom
field component or a "Generate codes" button).

## Transport planning

Two sides: attendees self-report (the `/events/:slug/travel` form above, writing
`EventTransportPrefs`); admins group the carpool. This section is the **admin
planner** that consumes those prefs — an evolution of the legacy `/eat/:slug`
view, which was admin-only and made the admin type *everyone's* locations.

The admin planner is one custom Payload view per event at
`/admin/collections/events/:id/transport` — a single React component with
client-side state + debounced autosave, just like legacy.

### What it does

- **Roster + their self-reported prefs**: pulls **confirmed** `Registrations`
  for the event *joined to* each one's `EventTransportPrefs`. Two v2 wins over
  legacy: Registrations already store `name` + `phone` (the 3-source name
  reconstruction `PaidMembers` → `people` → email-prefix is *gone*), and the
  admin no longer types locations — each row already shows the attendee's start,
  pickup, "driving?" and seats offered. Rows with no submitted prefs are flagged
  so the admin can chase them (or fill in a fallback).
- **Vehicles**: drivers come from who self-reported `own_vehicle` (capacity from
  their saved `Vehicle`); the admin can still add one manually. Editable per-trip
  capacity. Live seat meter with overflow warnings (`occupants/capacity`).
- **Pickup points** per vehicle, in route order: label, Google Maps link, time.
  The admin clusters attendees' reported *pickup locations* into a vehicle's
  route stops, then assigns people. One slot per person; a driver is never also a
  passenger (server normalizes on save — port legacy `normalizePlan`).
- **Departure/end math**: departure = first pickup's time; end = departure +
  estimated duration. Pure client-side, same as legacy.
- **Event-wide stops**: meals/detours (breakfast, lunch, lake) not tied to any
  vehicle — `{ type, label, mapsUrl, time }`.
- **WhatsApp export**: "Copy WhatsApp text" builds the shareable plain-text plan
  (port `buildWhatsApp`). Keep it — it's the actual artifact that gets shared.
- **Autosave**: debounced save + "unsaved changes" beforeunload guard.

Note the two distinct "pickup" concepts: an attendee's **pickup location** (in
`EventTransportPrefs` — *where they want to be met*) vs. a vehicle's **pickup
point** (in the plan blob — *a stop on that vehicle's route*). The admin's job is
mapping the former onto the latter.

### Persistence model (what changes vs legacy)

Three writers, cleanly separated (the whole point of splitting prefs out of the
blob): the **attendee** owns their `EventTransportPrefs` row + their
`SavedLocations`/`Vehicles`; the **admin** owns the `transportPlan` blob. No two
parties ever write the same record.

Legacy hand-rolled **five** API endpoints (`save-transport-plan`,
`add`/`update`/`delete`/`set-default-start-location`). In v2 almost all of that
is free:

- **The plan** is a `json` field (`Events.transportPlan`) — saved with a plain
  authenticated `PATCH /api/events/:id`. No custom save endpoint; a Payload
  `beforeChange` field hook runs the normalization (`normalizePlan`) that legacy
  did in its endpoint.
- **Saved locations & vehicles** are collections — full CRUD + set-default come
  from Payload's REST/local API for free. The "set default" + "dedupe label"
  rules live in collection hooks, not bespoke routes.
- **Attendee prefs**: the only bespoke route is the token-gated
  `/api/transport-prefs` (load + upsert), because anonymous attendees need
  scoped access Payload's auth doesn't grant out of the box.

The plan blob no longer duplicates per-person locations (that data lives in
`EventTransportPrefs` now) — it's just the admin's grouping decision, keyed by
email so it joins back to prefs:

```jsonc
{
  "version": 2,
  "vehicles": [{
    "id": "v1", "driverEmail": "...", "capacity": 4,
    "routeUrl": "", "estMinutes": 60, "collapsed": false,
    "pickups": [{ "id": "pk1", "label": "", "mapsUrl": "", "time": "04:00",
                  "passengerEmails": ["..."] }]
  }],
  "stops": [{ "id": "s1", "type": "Lunch", "label": "", "mapsUrl": "", "time": "" }]
}
```

(Bumped to `version: 2` — the legacy `hikers` location map is dropped; a one-line
migration in the hydrate path tolerates old blobs.)

Open question (Q-transport): **JSON blob vs. relational collections** for the
plan itself. The blob is pragmatic for admin-only ephemeral planning state and

Pickups / Assignments) is more Payload-native and queryable but is 3–4 more

**keep the blob** for the admin grouping; keep `SavedLocations`, `Vehicles`, and

## Reserved-spot allocation (the legacy race condition, fixed)

Legacy computed reserved spots on page render and never wrapped allocation
in a transaction. New flow:

```
POST /api/events/register
  ┌──────────────────────────────────────────────────────────────┐
  │  D1 transaction (or compensating-write equivalent on D1):    │
  │    1. SELECT paidCount, reservedHeldCount, maxAttendees      │
  │       FROM events WHERE id = ?                                │
  │    2. Compute available = maxAttendees - paidCount            │
  │       - reservedHeldCount (unless this user has a reserving   │
  │       discount code, then subtract it back)                   │
  │    3. If available <= 0 → 409                                 │
  │    4. INSERT registration (pending_payment)                   │
  │    5. (Don't bump counters yet — they bump on `confirmed`)    │
  └──────────────────────────────────────────────────────────────┘
```

D1 doesn't have multi-statement transactions in the Workers binding the
way Postgres does, but the D1 adapter exposes `db.batch([...])`. Where
true atomicity is needed, we use a single UPDATE with a WHERE guard
(optimistic concurrency) — e.g., on the webhook:

```sql
UPDATE events
SET paidCount = paidCount + 1
WHERE id = ? AND paidCount < maxAttendees - reservedHeldCount + ?  -- + reserved-back-out if applicable
```

If the row update affects zero rows → reject + refund. This is the only
clean way to be race-safe on D1.

Open question (Q4): are we OK with the (rare) "user paid but event sold
out between order-create and webhook" → automated refund flow? Yes, IMO,
as long as we surface it clearly. Better than overbooking.

## Driver-priority registration

A registration window where, for an opening period, **only people bringing a
vehicle can sign up** — so a hike never fills with passengers and no way to get
there. Drivers reserve their spot (and seats) first; general registration opens
later. (A solo motorbike counts — they're self-sufficient; their `seatsOffered`
just tells you how much passenger capacity they actually add.)

Driven by two Event timestamps:
- `driverRegOpensAt` → general registration is gated to drivers from here…
- `generalRegOpensAt` → …until here, when it opens to everyone.

(Set neither = open immediately. Set only `generalRegOpensAt` = a normal timed
open, no driver window.)

Flow:
- **Web** (`/events/:slug/register`): the page reads the window state and adapts.
  In the driver-only window it shows *"🚗 Early access — drivers first. You're
  registering as a driver; tell us your vehicle. General registration opens
  &lt;date&gt;."* and the form **requires** a vehicle + capacity (reuses the
  attendee `Vehicle` library so returning drivers pick, not retype). Outside the
  window it's the normal form. Before any window opens, a countdown / "opens
  &lt;date&gt;" state.
- **Server** (`/api/events/register`): the gate is enforced here, never trusted
  from the client. In the driver window, reject any registration that doesn't
  carry a vehicle declaration (and persist it as a `Vehicle` + seed the
  `EventTransportPrefs` row with `travelMode: own_vehicle`). This means a chunk
  of transport data is captured *at registration* for drivers — the planner
  starts pre-populated.

"Is this person a driver?" = they declared a vehicle in *this* registration.
We deliberately **don't** auto-admit someone just because they own a vehicle in
the library — bringing it to *this* event is a choice, so they affirm it each
time (prefilled from their default vehicle, one tap).

Open question (Q-driver): do we also want a hard *cap* on driver-window spots
(e.g. "first 10 drivers"), or is the window purely time-boxed? My vote: time-box
for v1; the existing `maxAttendees`/reserved-spot math already prevents
overfilling. Add a driver cap later only if a hike needs a passenger:driver ratio.
